# Cross-validation that doesn't leak

Cross-validation done naively on time-series data gives you optimistic out-of-sample scores. The culprits are autocorrelation and overlapping labels. The fix — purged k-fold with embargo — is a small change that makes a huge difference to honesty.

This chapter explains what goes wrong with standard CV, what `PurgedKFold` and `WalkForward` do differently, and how to use them. Both ship in `engine.backtest.cv`.

## Why standard k-fold leaks

Scikit-learn's `KFold` shuffles all your training samples and splits randomly. Suppose your label is "return over the next 5 days." Sample at time $t$ and sample at time $t+2$ have **80% label overlap** — they cover four of the same days.

If $t$ goes into training and $t+2$ goes into test, the model can essentially memorise — it knows the answer from a near-duplicate of the test sample.

The result: out-of-sample scores that look great in CV and fall apart in production.

## Purged k-fold

López de Prado's fix has two ingredients:

1. **Purge** — from each training fold, drop samples whose label horizon overlaps the test window.
2. **Embargo** — from the post-test side, drop samples for an extra buffer window before resuming training.

```python
from engine.backtest import PurgedKFold

cv = PurgedKFold(n_splits=5, purge=5, embargo=5)
for train_idx, test_idx in cv.split(n=len(X)):
    model.fit(X.iloc[train_idx], y.iloc[train_idx])
    score = evaluate(model, X.iloc[test_idx], y.iloc[test_idx])
```

`purge=5` matches a 5-day forward-return label. `embargo=5` (often set equal to purge or to a small multiple) blocks the model from "peeking" at test outcomes via right-side autocorrelation.

## The implementation

```python
@dataclass(frozen=True, slots=True)
class PurgedKFold:
    n_splits: int = 5
    purge: int = 0
    embargo: int = 0

    def split(self, n: int):
        fold_sizes = np.full(self.n_splits, n // self.n_splits)
        fold_sizes[: n % self.n_splits] += 1
        bounds, start = [], 0
        for size in fold_sizes:
            bounds.append((start, start + size))
            start += size

        all_idx = np.arange(n)
        for a, b in bounds:
            test = all_idx[a:b]
            keep = np.ones(n, dtype=bool)
            keep[a:b] = False
            if self.purge:
                keep[max(0, a - self.purge):a] = False
            if self.embargo:
                keep[b:min(n, b + self.embargo)] = False
            yield all_idx[keep], test
```

Twenty lines. The exact algorithm; no surprises.

## Walk-forward

For strategies you'll deploy live, walk-forward is the right CV — it mimics the actual production retraining cycle:

1. Train on $[0, T_0]$, test on $[T_0 + \text{embargo}, T_0 + \text{embargo} + \text{test_size}]$.
2. Train on $[0, T_0 + \text{test_size}]$, test on the next chunk.
3. Repeat.

```python
from engine.backtest import WalkForward

wf = WalkForward(initial_train=252 * 3, test_size=21, embargo=5)
for train_idx, test_idx in wf.split(n=len(X)):
    ...
```

A 3-year initial window, monthly test folds (21 trading days), 5-day embargo. The model retrains each month. Every test point is genuinely out-of-sample at the time of prediction.

For strategies where retraining is expensive (deep learning), you can use a **rolling window** instead of expanding: `train_idx = all_idx[t - W : t]` for a fixed window `W`. The course's implementation expands by default; modify the splitter for the rolling case.

## A worked example: walk-forward on a momentum classifier

```python
from sklearn.ensemble import GradientBoostingClassifier
from engine.backtest import WalkForward
import numpy as np
import pandas as pd

# X: features (lookback returns, vol, etc.); y: 1 if return in next 5 days > 0
def labels_from_returns(returns: pd.Series, horizon: int = 5) -> pd.Series:
    fwd = returns.rolling(horizon).sum().shift(-horizon)
    return (fwd > 0).astype(int)

X = build_features(prices)
y = labels_from_returns(returns, horizon=5)

wf = WalkForward(initial_train=252 * 3, test_size=21, embargo=5)
oos_probs = pd.Series(index=y.index, dtype=float)

for train_idx, test_idx in wf.split(n=len(X)):
    train_idx = train_idx[:-5]      # additional purge: drop last 5 of train (label horizon)
    model = GradientBoostingClassifier(n_estimators=100).fit(X.iloc[train_idx], y.iloc[train_idx])
    oos_probs.iloc[test_idx] = model.predict_proba(X.iloc[test_idx])[:, 1]

print(oos_probs.dropna().corr(returns.shift(-5).rolling(5).sum().reindex(oos_probs.index)))
```

The model retrains monthly on all data up to the test window's start (minus the purged tail), and each prediction is genuinely out-of-sample. The IC (information coefficient) of `oos_probs` vs forward returns is the cleanest measure of the model's edge.

## Combinatorial purged CV (preview)

A more aggressive variant: for $K$ folds, train on every $K-N$-sized combination of folds and test on the remaining $N$. This gives you many more train/test "paths" than k-fold and is the basis of the PBO (Probability of Backtest Overfitting) metric. Chapter 5 covers it.

## What to do with the CV results

Once you have an honest CV procedure, what do you *use* it for?

1. **Hyperparameter selection** — pick the hyperparameters that maximise CV score. Don't peek at the holdout.
2. **Model selection** — pick between gradient boosting and random forest by CV score.
3. **Sanity check on the final model** — is the CV score within reason? If your full-data model's CV score is much higher than walk-forward, something's leaking.
4. **Estimate of live performance** — the CV score is your honest prior on how the strategy will perform live.

## What NOT to do

- **Don't tune the embargo / purge to maximise the CV score.** That's leakage of a different kind.
- **Don't shuffle the training data within a fold for time-series labels.** Train order doesn't matter for tree-based models but does for many neural architectures.
- **Don't refit on the test set "to see if the score improves".** It will. It's also meaningless.

## Pitfalls

!!! warning "Small embargo on serially-correlated features"
    Even with purge equal to the label horizon, features can have longer-range autocorrelation. If your feature is "60-day rolling Sharpe", a 5-day embargo is too small. Embargo should be at least as long as the longest feature lookback if the feature includes the label.

!!! warning "Walk-forward with too-frequent retraining"
    Daily retraining sounds like the most honest, but typically picks up too much noise. Monthly retraining is a reasonable starting point.

!!! warning "Cross-sectional samples"
    For panel data (multiple symbols at the same date), a "sample" is one symbol-date. Two samples at the same date are not redundant; two samples for the same symbol on consecutive dates are. Purge by date, not by row index.

## Bottom line

For any model that produces a forecast at time $t$ using data up to time $t$:

- **Purged k-fold** with purge ≥ label horizon, embargo ≥ feature lookback's longest tail — for hyperparameter sweeps.
- **Walk-forward** — for honest "what would this strategy have produced live" simulations.
- **Combinatorial purged CV** — when you need rigorous PBO numbers (chapter 5).
